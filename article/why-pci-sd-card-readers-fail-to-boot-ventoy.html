Why PCI SD Card Readers Fail to Boot Ventoy

Many users find that an SD card loaded with Ventoy boots reliably through an inexpensive external USB adapter, yet fails completely when inserted into a laptop's built-in, PCI-based SD card slot. This discrepancy occurs because computer firmware provides standardized, universal boot support for USB mass storage devices, while built-in PCI Express (PCIe) SD card controllers lack the firmware-level drivers necessary for early-stage system initialization.

Lack of UEFI and BIOS Firmware Drivers

For a system to boot from any storage device, the motherboard's UEFI or legacy BIOS must establish communication with that device before an operating system or bootloader loads. Motherboard firmware universally includes native drivers for the USB Mass Storage Class standard (USB BOT and UAS). As a result, when an SD card is placed in a USB card reader, the computer treats it as a standard USB flash drive and can read its partition table immediately.

Conversely, built-in card readers are connected directly to the system's PCI or PCIe bus, commonly manufactured by vendors like Realtek, Genesys Logic, or BayHub. These controllers require specialized Driver Execution Environment (DXE) drivers under UEFI, or standard Option ROMs under legacy BIOS, to expose the SD card as a bootable block device. Because motherboard and laptop manufacturers rarely license or bundle these vendor-specific storage drivers into their system firmware, the BIOS cannot recognize the card as a viable boot target.

The Standardized USB Bridge vs. Raw PCIe Controllers

An external USB card reader contains a dedicated bridge microcontroller. This chip translates the SD card’s native SPI or SD-bus signals into standard USB mass storage packets. To the computer, the medium is essentially indistinguishable from a generic USB thumb drive.

Internal card readers, on the other hand, communicate over the PCIe bus using the Secure Digital Host Controller Interface (SDHCI) or proprietary vendor protocols. While modern operating systems like Linux and Windows ship with device drivers to operate these PCIe controllers, those drivers are only activated after the OS kernel boots. During the pre-boot phase where Ventoy must initialize, the hardware remains dormant.

Ventoy's Multi-Stage Boot Requirements

Ventoy relies on a multi-stage boot architecture:

  1. Stage 1 (Firmware Hand-off): The system BIOS/UEFI accesses the Master Boot Record (MBR) or EFI System Partition (ESP) on the drive to launch Ventoy’s GRUB-based core.
  2. Stage 2 (Runtime Environment): Ventoy's runtime hooks into the system to locate the secondary partition holding your payload ISO files.
  3. Stage 3 (OS Kernel Initialization): The loaded ISO mounts its virtual media and transitions execution to the target operating system's kernel.

Even on rare hardware platforms where the UEFI firmware includes basic read-only drivers to execute Stage 1 from a PCIe card reader, the boot sequence typically breaks at Stage 2 or 3. Ventoy or the target Linux/Windows installer kernel often fails to map the virtual ISO image because the initialization scripts lack the low-level PCIe SDHCI kernel modules required to keep the link active during hand-off.

Conclusion

Because internal PCI-based SD card readers lack the firmware-level abstraction and early bootloader support granted to USB devices, they cannot reliably initiate or sustain Ventoy's multi-stage loading process. The simplest and most dependable solution remains using a standard USB-to-SD adapter, which bridges the card through the universally supported USB mass storage protocol.
