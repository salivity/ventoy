How vtoyboot Patches Linux VHDs for Ventoy

The vtoyboot tool allows standard Linux installations housed inside virtual disk images (such as .vhd or .img files) to boot natively via Ventoy on physical hardware. It achieves this by modifying the guest operating system's initial ramdisk (initramfs or initrd) to include specialized drivers, search scripts, and loop-mounting hooks. These modifications enable the Linux kernel to locate its host image on the Ventoy drive during early userspace initialization and mount it seamlessly as the root filesystem.

The Underlying Boot Dilemma

When Ventoy boots a virtual disk image, it relies on BIOS or UEFI firmware-level emulation (such as INT 13h or UEFI RAM-disk protocols) to present the virtual disk as a physical drive to the bootloader. However, once GRUB loads the Linux kernel, the kernel takes control of hardware management and discards firmware-level disk mappings.

Without modification, the kernel attempts to mount a root device (e.g., /dev/sda1 or a filesystem UUID) that no longer exists in physical space, resulting in a kernel panic or a drop to an emergency shell. The kernel must be made aware that its root filesystem is trapped inside an image file residing on a physical partition formatted as exFAT, NTFS, or ext4.

Detecting the Distribution and Initramfs Framework

The vtoyboot script is executed inside the virtual machine while the guest Linux system is running. Upon execution, the script identifies the host distribution's initramfs generation framework. It supports the major Linux init systems, including:

  • Dracut (Fedora, RHEL, CentOS, openSUSE)
  • initramfs-tools (Debian, Ubuntu, Linux Mint)
  • mkinitcpio (Arch Linux, Manjaro)

By identifying the active framework, vtoyboot determines where to inject its custom hooks and configuration files.

Injecting Early Userspace Hooks

The core of vtoyboot consists of custom scripts and binaries (such as vtoy_mount or Dracut modules) placed into the system directories where the initramfs generator sources its components.

These injected scripts alter the early boot sequence:

  1. Hardware and Filesystem Modules: The script ensures that storage drivers for physical interfaces (USB, NVMe, SATA) and filesystem drivers for the host Ventoy drive (such as exfat, ntfs3, or fuse) are forced into the generated initramfs image.
  2. Loop Device Support: It enables the loopback block driver (loop) and device mapper modules inside the initramfs, which are necessary to map a raw disk file to a block device.

Execution During the Early Boot Process

Once the patched system boots via Ventoy on physical hardware, the modified initramfs executes before the real root is mounted:

  1. Finding the Host Partition: The injected hook searches physical disks for the Ventoy boot environment and the parent drive where the .vhd resides.
  2. Loop-Mounting the Disk Image: The script identifies the specific VHD file path passed by the bootloader parameters, mounts the host filesystem read-only or read-write, and attaches the virtual disk image to a loop device (e.g., /dev/loop0).
  3. Partition Mapping: The partitions within the virtual disk image are exposed as sub-devices (e.g., /dev/loop0p1, /dev/loop0p2) using kpartx or the kernel's built-in partition-scanning capabilities.
  4. Pivoting Root: The initramfs mounts the designated root partition from the loop device to /sysroot or /newroot and completes the standard switch_root routine, handing control over to the guest system's systemd or init process.

Finalizing the Patch

Before exiting, vtoyboot automatically triggers the system's native command (update-initramfs -u, dracut -f, or mkinitcpio -P) to rebuild the initramfs images with the new hooks compiled directly into them. Once the machine is shut down, the resulting virtual disk file can be renamed with a .vtoy extension (e.g., linux.vhd.vtoy) and copied directly to a Ventoy USB drive for native hardware execution.
