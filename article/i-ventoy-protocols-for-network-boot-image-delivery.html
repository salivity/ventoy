iVentoy Protocols for Network Boot Image Delivery

iVentoy streamlines the network boot process by replacing standard slow transfer mechanisms with a modern, hybrid communication model. To boot operating systems and deliver ISO images across local networks and routed subnets, iVentoy relies on a combination of DHCP/ProxyDHCP, TFTP, and HTTP. This article breaks down the exact protocols iVentoy uses at each stage of the boot sequence, how image delivery works, and what is required to pass traffic across different network subnets.

DHCP and ProxyDHCP (Bootstrap Identification)

The initial connection relies on standard Dynamic Host Configuration Protocol (DHCP) or ProxyDHCP. When a client machine boots via PXE (Preboot Execution Environment), it broadcasts a DHCP discover packet to obtain network parameters.

  • Standard DHCP Mode: iVentoy can act as the primary DHCP server on the local subnet, assigning IP addresses directly along with DHCP Option 66 (Next Server IP) and Option 67 (Bootfile Name).
  • External/ProxyDHCP Mode: When an existing DHCP server handles IP assignments, iVentoy acts as a ProxyDHCP server (listening on UDP port 4011). It supplies only the PXE-specific boot information without interfering with standard IP allocation.

TFTP (Initial Bootloader Transfer)

Once the client receives the network address and bootfile location, it uses Trivial File Transfer Protocol (TFTP) over UDP port 69.

TFTP is historically the standard for PXE, but it is slow and inefficient for large payloads. iVentoy restricts TFTP usage strictly to the initial stage. It transmits only small, essential network boot files (such as iPXE binaries and the core bootloader) to initialize the client's network stack and prepare it for high-speed transfer.

HTTP (High-Speed Image Delivery)

The defining feature of iVentoy's architecture is its reliance on HTTP (Hypertext Transfer Protocol) over TCP (typically port 26000 by default) for actual image payload delivery.

Once the initial TFTP-delivered iPXE environment initializes, execution switches to HTTP. Rather than transferring multi-gigabyte ISO files via TFTP, iVentoy serves the boot environment, operating system files, and raw ISO contents through HTTP streams. This drastically reduces transfer times, improves reliability, and ensures compatibility across modern network switches.

Cross-Subnet Delivery Considerations

Delivering boot images across different subnets requires specific network routing and relay configurations, as broadcast-based PXE requests do not cross router boundaries by default:

  • DHCP Relay / IP Helper: Network routers or Layer 3 switches must be configured with DHCP relay agents (IP helpers) pointing to the iVentoy server’s IP address. This forwards the initial broadcast packets from foreign subnets to the iVentoy server.
  • Option 66 and Option 67: If using an enterprise DHCP server across subnets, configuring DHCP Scope Options 66 (iVentoy IP) and 67 (bootloader file name, such as iventoy_loader_16000) directs the client to the iVentoy host.
  • Port Routing: Firewalls and routing tables between subnets must permit UDP port 67/68 (DHCP), UDP port 69 (TFTP), UDP port 4011 (ProxyDHCP, if used), and the configured TCP HTTP port (default 26000) to allow end-to-end communication from the client to the server.
