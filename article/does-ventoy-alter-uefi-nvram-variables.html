Does Ventoy Alter UEFI NVRAM Variables?

Using Ventoy to boot multiple operating systems generally does not alter persistent UEFI NVRAM variables on the host motherboard during standard operations. Because Ventoy operates primarily from the USB drive and system memory, it leaves the host's firmware settings intact. The sole persistent exception occurs when using Ventoy with UEFI Secure Boot enabled, which requires enrolling a Machine Owner Key (MOK) into the motherboard's NVRAM.

Standard Booting and NVRAM

Under standard boot conditions with Secure Boot disabled, Ventoy does not modify UEFI NVRAM. When your system boots Ventoy, the motherboard’s UEFI firmware executes the default fallback bootloader path (\EFI\BOOT\BOOTX64.EFI) directly from the removable drive. Ventoy initializes its GRUB-based environment entirely in system RAM and reads disk images (ISOs, IMGs, or VHDs) straight from the flash drive. It does not invoke UEFI runtime services like SetVariable() to create persistent BootXXXX entries, change the system boot order, or write persistent configuration data to the motherboard.

The Secure Boot Exception: MOK Enrollment

If Secure Boot is active on the host machine, Ventoy relies on the standard Linux shim loader to authenticate its binaries. Because Ventoy’s custom keys are not signed by Microsoft’s default third-party UEFI Certificate Authority, the system will prompt you to enroll Ventoy’s public key via the MokManager interface.

Enrolling this key permanently writes Ventoy's certificate to the MokList variable within your motherboard’s NVRAM. This is a deliberate, persistent modification designed to allow the system to trust Ventoy on subsequent boots without disabling Secure Boot. If you want to avoid writing to NVRAM entirely, you must disable Ventoy’s Secure Boot support via the Ventoy configuration utility or disable Secure Boot directly within your motherboard's UEFI setup.

Host Firmware Behavior vs. Ventoy Actions

It is important to distinguish between Ventoy's actions and the automatic behavior of the host motherboard's UEFI firmware:

  • Automatic Boot Option Cache: Some UEFI implementations automatically create transient or semi-permanent boot entries in NVRAM when a new USB drive containing an EFI system partition is detected. This is executed by the motherboard's own firmware logic, not by Ventoy code.
  • Booted Operating System Installers: While Ventoy itself does not alter NVRAM, operating system installers booted through Ventoy (such as Windows Setup or a Linux distribution installer) will interact with UEFI NVRAM. These installers routinely call SetVariable() to register new boot options and set themselves as the primary boot target.

Outside of the optional Secure Boot Machine Owner Key enrollment, Ventoy functions in a completely stateless manner relative to the host machine's NVRAM, leaving your motherboard firmware clean upon drive removal.
