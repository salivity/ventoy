How Ventoy Intercepts BIOS and UEFI Disk Read Requests

Ventoy boots operating systems directly from ISO, WIM, and IMG files without extraction by establishing an in-memory virtualization layer at the firmware level. To trick operating system bootloaders into believing an unextracted disk image is a physical optical disc or drive, Ventoy intercepts disk read requests before the kernel initializes. It accomplishes this by hooking the legacy BIOS Interrupt 13h (INT 13h) handler and overriding the UEFI EFI_BLOCK_IO_PROTOCOL. By actively translating virtual sector addresses into the real physical sector locations of the container file, Ventoy supplies requested data seamlessly without relying on pre-extracted media.

The Virtual Mapping Foundation

Before intercepting I/O requests, Ventoy builds a sector-mapping table. When an ISO file is selected from the Ventoy boot menu, the Ventoy core parses the underlying file system (typically exFAT or NTFS) on the physical USB drive. Because files can be fragmented, Ventoy identifies every physical cluster where the target ISO resides and constructs an in-memory lookup table that pairs the ISO's internal logical block addresses (LBAs) with the USB drive's physical LBAs.

Intercepting Legacy BIOS Requests via INT 13h

In legacy BIOS environments, operating system bootloaders access storage hardware through software interrupts using the Interrupt Vector Table (IVT), located in the lowest memory segment (0x0000:0x0000 to 0x0000:0x03FF). Disk operations are routed through vector 0x13.

  1. Vector Swapping: Ventoy allocates a reserved memory region in low conventional memory (often using a TSR-like method or reserving memory below the Extended BIOS Data Area) to house its custom INT 13h handler. It saves the pointer to the original BIOS ROM disk handler and rewrites the INT 13h vector in the IVT to point to its own hook.
  2. Drive Emulation: Ventoy registers a virtual drive number (typically 0x80 for an emulated hard drive or 0x9F/0xE0 for an emulated optical drive).
  3. Request Filtering: When a bootloader executes an INT 13h call (such as Function AH=02h for standard reads or AH=42h for extended LBA reads), Ventoy's hooked handler inspects the registers.
  4. LBA Translation: If the requested drive matches the virtual drive ID, Ventoy intercepts the request. It takes the requested virtual sector offset, cross-references it with the pre-calculated sector map, and converts it into the exact physical sector location of the ISO file on the USB drive.
  5. Execution and Return: Ventoy modifies the register parameters to target the physical drive ID and the translated physical LBA, forwards the read call to the original BIOS INT 13h handler, and returns the retrieved data to the bootloader buffer, clearing error flags to simulate native read success.

Intercepting Modern UEFI Requests via Block I/O

UEFI firmware does not use CPU interrupts or real-mode memory vectors. Instead, it relies on modular protocols published in a centralized system database. Storage devices expose their read and write capabilities primarily through the EFI_BLOCK_IO_PROTOCOL and EFI_BLOCK_IO2_PROTOCOL.

  1. Protocol Implementation: Ventoy instantiates a synthetic UEFI device handle representing the virtual disk. It installs an instance of EFI_BLOCK_IO_PROTOCOL on this handle, configuring the EFI_BLOCK_IO_MEDIA structure to advertise the properties of the ISO (such as read-only status, total sector count, and sector size).
  2. Function Pointer Hooking: In scenarios where existing firmware drivers must be redirected, Ventoy replaces the original ReadBlocks function pointer inside the target protocol interface table with its own wrapper function.
  3. Intercepting ReadBlocks: When an EFI bootloader (such as bootx64.efi) issues a BlockIo->ReadBlocks() call against the virtual handle, execution directs to Ventoy's wrapper.
  4. Physical Delegation: Ventoy accepts the LBA, BufferSize, and destination Buffer parameters from the caller. It looks up the physical sector distribution of the ISO file on the host storage and invokes the native, unmodified EFI_BLOCK_IO_PROTOCOL of the physical USB drive to pull the raw sectors into the caller's target buffer.

Handover to the Operating System Kernel

Both BIOS INT 13h and UEFI Block I/O hooks only persist while firmware services remain active. Once an operating system kernel loads its own hardware drivers and calls ExitBootServices() under UEFI or enters Protected/Long Mode under BIOS, firmware-level hooks are bypassed.

To bridge this gap, Ventoy patches the boot sequence (such as injecting hook scripts into a Linux initramfs or utilizing runtime drivers in Windows) to locate the ISO file on the physical partition and remount it as a loopback block device inside the running operating system before root file system mounting occurs.
