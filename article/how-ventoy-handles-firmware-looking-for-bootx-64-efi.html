How Ventoy Handles Firmware Looking for bootx64.efi

Certain UEFI firmware implementations strictly adhere to the default removable media specification and will only execute \EFI\BOOT\BOOTX64.EFI, ignoring custom NVRAM boot paths. Ventoy handles this limitation by designing its storage structure around standard UEFI compliance: it places its primary loader or Secure Boot shim directly at \EFI\BOOT\BOOTX64.EFI on a dedicated hidden EFI partition. When an ISO is selected, Ventoy relies on in-memory UEFI driver hooking rather than physical file swapping, allowing systems with restrictive firmware to boot seamlessly.

The Removable Media Specification Compliance

Under the standard UEFI specification, removable storage devices without pre-registered NVRAM boot variables rely on a predefined fallback path to initiate a boot sequence. For 64-bit x86 systems, this path is hardcoded as \EFI\BOOT\BOOTX64.EFI.

Certain motherboard vendors and older UEFI implementations do not scan for alternative files or allow flexible boot path selection. Ventoy handles this natively by partitioning the target drive into two distinct sections during installation:

  1. Partition 1: A large exFAT, NTFS, or ext4 partition that holds the user's raw ISO, WIM, or IMG files.
  2. Partition 2 (VTOYEFI): A small FAT-formatted EFI System Partition (ESP) containing the core boot environment.

Within the VTOYEFI partition, Ventoy structures its directories according to the fallback specification, ensuring the file \EFI\BOOT\BOOTX64.EFI is present at the exact location the firmware expects.

Handling Secure Boot via Shim

When Secure Boot is enabled, the firmware verifies the digital signature of bootx64.efi before execution. Ventoy addresses this by using a Microsoft-signed Shim loader as its default BOOTX64.EFI.

  1. The system firmware locates and executes \EFI\BOOT\BOOTX64.EFI (the signed Shim).
  2. The Shim verifies Ventoy’s custom key or prompts the user via MokManager to enroll the key.
  3. Once validated, the Shim chains execution to Ventoy's actual core bootloader, grubx64.efi, located within the same directory.

If Secure Boot is disabled in the Ventoy settings or the system firmware, Ventoy can place its GRUB-based loader directly as BOOTX64.EFI, bypassing the intermediate Shim layer entirely.

In-Memory Hooking for ISO Payloads

A challenge arises when an ISO image selected by the user also relies on its own internal \EFI\BOOT\BOOTX64.EFI. If the firmware were to read directly from the drive's file structure, a collision or execution failure would occur.

Ventoy solves this through runtime memory hooking:

  • Ventoy does not unpack or write the ISO’s files onto the physical USB partition.
  • Instead, Ventoy’s loader installs a custom UEFI runtime driver that hooks the standard UEFI BlockIO protocol.
  • Ventoy maps the chosen ISO into memory as a virtual optical disc or virtual drive.
  • Ventoy hands control to the ISO’s own \EFI\BOOT\BOOTX64.EFI within this virtualized environment.

Because the system firmware has already executed Ventoy’s physical bootx64.efi at initial boot, the subsequent execution of the payload's bootx64.efi takes place inside the hooked environment, satisfying both the firmware's strict search requirements and the target operating system's installation structure.
