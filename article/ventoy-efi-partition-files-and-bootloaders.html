Ventoy EFI Partition Files and Bootloaders

When Ventoy installs onto a USB drive, it creates a dedicated, hidden EFI System Partition (ESP) labeled VTOYEFI formatted with a FAT filesystem. This article breaks down the exact bootloaders, security keys, and system files housed inside this partition, explaining how they enable Ventoy to boot across multiple hardware architectures with Secure Boot compatibility.

Partition Overview

Ventoy splits storage into two main partitions:

  1. Partition 1 (Ventoy): A large, user-accessible partition (formatted in exFAT, NTFS, or ext4) used strictly for storing ISO, IMG, WIM, and VHD files.
  2. Partition 2 (VTOYEFI): A small (typically 32MB) FAT16/FAT32 partition containing the actual boot environment, architecture-specific UEFI binaries, and GRUB configurations required to launch the interface.

Key Directories and Files in VTOYEFI

1. /EFI/BOOT/ (UEFI Fallback and Bootloaders)

This directory houses standard UEFI fallback executables that motherboard firmware searches for when initializing a removable USB device:

  • BOOTX64.EFI: The primary 64-bit x86 UEFI bootloader. In Secure Boot-enabled setups, this is typically a signed Shim bootloader compiled with a Microsoft Third-Party UEFI CA signature. It verifies and chains into GRUB.
  • BOOTIA32.EFI: The 32-bit x86 UEFI bootloader for older tablets and hybrid devices with 32-bit UEFI firmware (even if paired with 64-bit CPUs).
  • BOOTAA64.EFI: The 64-bit ARM (AArch64) bootloader for ARM-based systems.
  • BOOTRISCV64.EFI / BOOTMIPS.EFI: Bootloaders compiled for RISC-V and MIPS architectures in newer Ventoy releases.
  • grubx64.efi, grubia32.efi, grubaa64.efi: The actual GRUB2 core binaries corresponding to each CPU architecture. When BOOTX64.EFI (Shim) executes, it verifies and loads grubx64.efi.
  • mmx64.efi / mmia32.efi / mmaa64.efi: MokManager (Machine Owner Key Manager) binaries. These execute automatically if Secure Boot fails verification, allowing users to enroll Ventoy’s custom certificate into the device's NVRAM.

2. /EFI/ventoy/ (Keys and Certificates)

This folder holds the cryptographic assets required for Secure Boot:

  • ventoy.cer: Ventoy's public certificate (DER format). Users enroll this key via MokManager to allow GRUB and subsequent kernel components to pass UEFI Secure Boot checks without modifying motherboard firmware security settings.

3. /ventoy/ (GRUB Environment and Core Assets)

This directory houses the internal configuration files, runtime scripts, and modules needed to construct the Ventoy graphical interface and parse ISO files:

  • ventoy.disk.img: A compressed loopback disk image containing the secondary runtime environment, drivers, device-mapper scripts, and disk emulation modules used to hook ISO virtual drives into memory.
  • GRUB Modules (*.mod): A collection of dynamic GRUB2 modules compiled for filesystem detection (NTFS, exFAT, ext2/3/4, Btrfs, XFS, FAT), graphical user interface rendering, partition table parsing, and crypto hashing.
  • Font and Theme Assets: Files such as unicode.pf2 and theme-specific assets required to render the GRUB boot menu at high resolutions.
  • Architecture-Specific Boot Images: Binaries such as core.img or boot.img used when booting under legacy BIOS/MBR modes via the partition's master boot record pointers.

How These Files Work Together

  1. Firmware Detection: The motherboard's UEFI firmware locates /EFI/BOOT/BOOTX64.EFI (or architecture equivalent).
  2. Secure Boot Check: If Secure Boot is enabled, the firmware verifies the Microsoft signature on the Shim loader. If unverified, the user enrolls ventoy.cer via mmx64.efi.
  3. GRUB Execution: Shim passes control to grubx64.efi, loading internal GRUB modules and displaying the UI.
  4. Virtual Emulation: Once an ISO is selected, Ventoy uses the modules and routines stored in ventoy.disk.img to map the target image as a virtual device before handing execution over to the operating system's kernel.
