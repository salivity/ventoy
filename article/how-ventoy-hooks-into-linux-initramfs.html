How Ventoy Hooks into Linux Initramfs

Ventoy enables direct ISO booting by injecting a custom secondary initramfs image into memory alongside the operating system's native initramfs during the bootloader stage. Because Linux drops BIOS/UEFI disk abstractions once the kernel loads, standard distribution scripts fail to locate the installation media stored inside an unmounted ISO file. Ventoy overcomes this by concatenating its own archive (ventoy.cpio) to the boot pipeline, executing specialized scripts that mount the physical storage partition, map the ISO to a loop device, and spoof the underlying distribution's volume identifiers before the root filesystem switch occurs.

The Problem of Direct ISO Booting

When a Linux distribution boots from standard media, the BIOS or UEFI loads a bootloader, which in turn loads the Linux kernel and an initial RAM disk (initramfs). The native initramfs contains minimal drivers and scripts designed to scan physical storage controllers (like USB or SATA) for a disk partition matching a hardcoded volume label or UUID.

When booting an ISO file directly from an existing filesystem (such as exFAT or NTFS), the kernel boots, but its native initramfs scripts do not know that the installation data is trapped inside an ISO container. Because Linux switches to native hardware drivers, any temporary disk emulation provided by UEFI firmware disappears, causing standard distributions to crash with "root device not found" errors.

CPIO Concatenation at the Bootloader Level

Ventoy solves this in the GRUB bootloader phase without modifying the ISO file on disk. The Linux kernel has native support for multiple, concatenated initramfs archives passed through the bootloader:

initrd /path/to/distro-initrd.img /ventoy/ventoy.cpio

When the kernel initializes, it extracts these CPIO archives sequentially into rootfs (tmpfs). Ventoy loads its own small CPIO archive on top of the original initramfs. Any files in Ventoy’s archive will sit alongside, or overwrite, the distribution’s existing scripts in the virtual root filesystem before user space initializes.

Hooking the Early User Space

Once the kernel completes hardware enumeration, it hands control to /init inside the initramfs. Ventoy’s payload hooks into this environment using different strategies depending on the distribution's init framework:

  • Hooking Native Init Frameworks: Ventoy injects hooks directly into common framework directories, such as Dracut (/usr/lib/dracut/modules.d/), Casper (Ubuntu), Live-boot (Debian), and Mkinitcpio (Arch Linux).
  • Replacing or Wrapping /init: If the distribution uses a generic or non-modular init system, Ventoy renames the distribution's original /init script and substitutes its own wrapper script. The wrapper executes Ventoy's setup routines first and then calls the original entry point.

The Ventoy Loopback and Spoofing Sequence

Once Ventoy's injected script gains execution within the initramfs, it performs the following steps:

  1. Reading Boot Parameters: Ventoy retrieves the exact physical partition and file path of the ISO, which the GRUB stage passed down via kernel command-line arguments or dedicated runtime memory configurations.
  2. Polling and Mounting the Host Partition: The script waits for the kernel to initialize the host USB controller and disk devices. Once the physical device is online, Ventoy mounts the underlying partition (exFAT, NTFS, ext4, etc.) containing the ISO file.
  3. Creating the Loop Device: The script runs losetup to bind the ISO file to a virtual loop device (e.g., /dev/loop0).
  4. Emulating Device Signatures: Modern distribution scripts look for specific devices, such as /dev/disk/by-label/DISTRO_LABEL or /dev/disk/by-uuid/XXXX-XXXX. Ventoy's hooks create matching symbolic links pointing directly to the newly generated loop device or inject udev rules to populate these nodes automatically.

Clean Hand-Off to the Target System

With the ISO loop-mounted and device nodes linked to mimic native physical media, Ventoy allows the distribution's original boot logic to resume. When the native initramfs scripts scan the system for installation media or the live squashfs image, they detect the loop device as if it were a physical CD-ROM or burned USB drive.

The distribution successfully mounts the live root filesystem, and the native initramfs completes its execution by pivoting to the real root directory (switch_root), transitioning smoothly into the fully initialized Linux operating system.
