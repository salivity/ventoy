Ventoy UEFI Variable Access on Restrictive Firmware

Certain motherboard firmware implementations strictly limit or completely block operating systems and third-party bootloaders from accessing or writing to UEFI runtime variables (NVRAM). This article explains how Ventoy overcomes these restrictive firmware environments by intercepting standard UEFI runtime services, virtualizing variable storage in system memory, and bypassing persistent NVRAM dependencies during the multi-boot process.

The Challenge of Restrictive UEFI NVRAM

In standard UEFI architectures, bootloaders rely on NVRAM variables via the GetVariable and SetVariable runtime services to store boot configurations, read Secure Boot states, and pass execution context between different stages of the boot process.

However, many modern or proprietary motherboards enforce strict security policies or contain buggy firmware implementations that reject SetVariable calls from non-signed payloads, mark runtime variables as read-only, or lock down NVRAM access after ExitBootServices() is called. When a dynamic boot tool like Ventoy attempts to save state or modify the boot order, these restrictive environments trigger standard system halts, write-protection faults, or silent failures.

Hooking the UEFI Runtime Services Table

To circumvent these restrictions, Ventoy does not rely solely on direct hardware NVRAM writes. Instead, during its initial execution stage, Ventoy intercepts the global UEFI System Table (EFI_SYSTEM_TABLE). Specifically, it hooks the function pointers inside the EFI_RUNTIME_SERVICES table:

  1. Service Redirection: Ventoy replaces the default pointers for GetVariable, SetVariable, and GetNextVariableName with its own internal handler functions.
  2. Call Filtering: When a subsequent payload, kernel, or chainloaded bootloader calls a variable service, the request hits Ventoy's hook first rather than the restrictive motherboard firmware.
  3. Hardware Pass-Through: For non-critical standard queries, Ventoy forwards the request down to the original firmware handlers, preserving compatibility with native hardware routines.

In-Memory Variable Virtualization

When the firmware returns an error indicating that NVRAM is locked, write-protected, or unavailable, Ventoy activates an in-memory variable emulation layer:

  • Shadow Tables: Ventoy allocates an isolated, reserved memory space in RAM to serve as a virtual NVRAM table.
  • State Interception: Calls to SetVariable that would typically fail on the motherboard are stored directly in this allocated RAM structure.
  • Seamless Retrieval: Any subsequent GetVariable call targeting Ventoy-specific states or modified environment paths retrieves the data from this memory cache, completely bypassing physical NVRAM.

Because this memory is marked as reserved within the UEFI memory map, it survives the handoff process until the secondary bootloader or kernel takes full control of memory management.

Parameter Passing via Kernel Command Lines

Because in-memory UEFI variables do not persist across hard reboots, Ventoy eliminates the need to permanently store variable states for ISO booting. Ventoy dynamically constructs the boot path by directly modifying the kernel command line parameters (such as supplying specific disk signatures and file paths) in memory.

By passing boot data directly through memory-resident arguments rather than relying on persistent UEFI variables, Ventoy ensures that the operating system's initramfs can locate and mount the dynamic virtual disk even if the motherboard refuses to acknowledge custom UEFI environment entries.

Secure Boot and Shim Integration

On systems where variable access is restricted specifically by Secure Boot policies, Ventoy operates through a signed shim loader utilizing the Machine Owner Key (MOK) architecture.

Rather than attempting to write custom keys directly into the motherboard’s secure NVRAM—which restrictive firmware routinely prevents—Ventoy validates its internal GRUB image and runtime hooks using its own embedded certificates managed by the shim layer in temporary runtime memory. This architecture ensures variable isolation while remaining compliant with restrictive UEFI platform keys.
