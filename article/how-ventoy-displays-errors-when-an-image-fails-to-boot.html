How Ventoy Displays Errors When an Image Fails to Boot

When an ISO or image file fails to launch, Ventoy alerts the user through a combination of graphical dialog windows, text-based console messages, and return status prompts driven by its underlying GRUB2 core. This article breaks down the exact mechanisms Ventoy uses to present boot failure codes, how it visualizes system halts, and the difference between Ventoy-level initialization errors and operating system handoff failures.

Graphical and Terminal Dialog Boxes

Ventoy primarily operates within a GRUB-based environment. When an image fails before the operating system kernel can take over, Ventoy intercepts the error and presents a message box directly over the boot menu interface:

  • Text-Based Alert Windows: If an image format is unsupported, corrupted, or has an invalid structure, Ventoy triggers a bordered text dialog. This window explicitly describes the issue (such as "No bootfile found" or "File format error") and halts execution.
  • Return Prompts: Most failures pause the bootloader completely, appending a message such as Press ENTER to return to the menu... at the bottom of the screen. This prevents the machine from entering an infinite reboot loop.

Common On-Screen Error Messages and Codes

Rather than relying on numeric hexadecimal codes alone, Ventoy displays descriptive string errors that indicate where the process failed:

  • Memory Allocation Errors: When attempting to boot using the Memdisk mode on systems without sufficient RAM, Ventoy displays an out-of-memory notification indicating that the system cannot allocate contiguous space for the target image.
  • Compatibility and Architecture Mismatches: If you attempt to boot a 32-bit UEFI image on a 64-bit-only UEFI motherboard, Ventoy prints a direct architecture mismatch warning immediately after selecting the file.
  • Cluster and Fragment Errors: If an ISO file is excessively fragmented or stored across bad sectors on the USB drive, Ventoy will output read failure notifications during the virtual disk mapping phase.

UEFI Secure Boot Violations

If an image fails due to platform security policies, the error does not generate from the Ventoy script itself, but from the UEFI firmware layer:

  • Security Violation Screens: Systems with Secure Boot enabled will display blue or black firmware screens with messages such as Verification failed: (0x1A) Security Violation.
  • MokManager Prompts: When Ventoy's keys are not yet enrolled, the display will route to the "Enroll Key" (MokManager) interface instead of the standard operating system loading screen, signifying an authentication block.

Ventoy Failure vs. Kernel Handoff Failure

It is vital to distinguish where the error display originates:

  1. Ventoy-Level Errors: Displayed in the Ventoy native theme or simple monochrome text on the GRUB console. These represent issues where Ventoy cannot map, parse, or inject its runtime hooks into the image.
  2. OS-Level Errors: Displayed via kernel panic text, an initramfs rescue shell, or a Dracut emergency prompt (e.g., dracut-initqueue timeout). In this state, Ventoy has successfully executed the initial bootloader, but the operating system cannot locate its virtual CD/DVD block device to complete the boot process.

Capturing Verbose Debug Output

When an image fails silently or drops back to the menu instantly, Ventoy includes a verbose debug option:

  • Pressing the designated function key (typically F5 Tools, or utilizing the text-mode menu) allows users to enable debug logging.
  • In debug mode, Ventoy bypasses the graphical splash screen and prints step-by-step hook executions line-by-line across the console, making it possible to identify the exact shell function or sector call that triggered the failure.
