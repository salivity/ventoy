How Ventoy Handles Multi-Architecture ISO Files

Ventoy streamlines booting multi-architecture ISO files by dynamically adapting to the host machine's hardware environment before launching the operating system. Rather than modifying or extracting the contents of an ISO, Ventoy detects the host firmware mode—whether it is Legacy BIOS, x86_64 UEFI, IA32 UEFI, or ARM64 UEFI—and chains execution directly to the corresponding bootloader embedded inside the ISO. This article explains the technical mechanics behind how Ventoy identifies, maps, and executes multi-architecture ISO images seamlessly.

Host-Side Firmware Detection

When a computer boots into Ventoy, the process begins entirely outside of the ISO file. Ventoy installs a multi-partition layout on the USB drive containing distinct boot binaries tailored for different architectures (such as bootx64.efi, bootia32.efi, bootaa64.efi, and a standard MBR code for Legacy BIOS). The host motherboard automatically loads the Ventoy binary that corresponds to its native architecture and firmware mode. Consequently, Ventoy is already running in the correct architectural context before the user even selects an ISO from the menu.

Dynamic Bootloader Chainloading

Multi-architecture ISO files, such as hybrid Linux distributions or multi-version Windows installers, contain multiple boot paths internally. They typically feature an El Torito boot catalog for Legacy BIOS alongside an EFI system partition containing bootloaders for various UEFI architectures (e.g., /EFI/BOOT/BOOTX64.EFI, /EFI/BOOT/BOOTIA32.EFI, or /EFI/BOOT/BOOTAA64.EFI).

Once an ISO is selected, Ventoy handles the multi-architecture structure as follows:

  • Legacy BIOS Mode: Ventoy parses the ISO's El Torito specifications, extracts the BIOS boot image (often an isolinux or GRUB stage), and executes it using standard INT 13h disk emulation interrupts.
  • UEFI Modes (x86_64, IA32, ARM64): Ventoy inspects the embedded EFI system partition inside the ISO. It searches for the boot file that strictly matches the currently running UEFI environment. For example, on a 32-bit UEFI tablet, it locates and hands control over to BOOTIA32.EFI, while on a standard modern PC, it hands control to BOOTX64.EFI.

In-Memory Virtualization and Hooking

Ventoy avoids altering the ISO structure on disk. Instead, it creates a virtual disk in memory that maps the sectors of the selected ISO file back to the physical USB storage.

During the handoff:

  1. Ventoy hooks the firmware's storage protocols (such as EFI_BLOCK_IO_PROTOCOL in UEFI or BIOS interrupt vectors).
  2. When the ISO's architecture-specific bootloader queries the firmware for attached storage, Ventoy intercepts the request and presents the ISO image as a standard optical drive or physical block device.
  3. The selected architecture's bootloader executes normally, reading its respective kernel, drivers, and initial RAM disk (initrd) directly from the virtualized image.

By letting the host firmware dictate the initial environment and then delegating execution to the corresponding architecture-specific file inside the ISO, Ventoy achieves full compatibility with multi-architecture images without requiring manual user configuration or file modification.
