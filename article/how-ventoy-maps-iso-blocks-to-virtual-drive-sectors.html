How Ventoy Maps ISO Blocks to Virtual Drive Sectors

Ventoy boots operating system installers directly from raw ISO files without extracting them by dynamically constructing an in-memory translation layer. Instead of loading an entire multi-gigabyte ISO into RAM, Ventoy analyzes the host file system to locate the file's exact physical storage blocks on the USB drive, builds a sector-mapping table in memory, and hooks firmware-level disk access interfaces to emulate a physical CD/DVD-ROM drive in real time.

1. File Extent Discovery

Before any virtualization occurs, Ventoy's core bootloader must determine where the ISO file physically resides on the USB drive's underlying storage. Ventoy includes read-only drivers for standard file systems such as exFAT, NTFS, ext4, XFS, and FAT32.

When an ISO is selected from the boot menu, Ventoy reads the file system allocation structures (such as exFAT file allocation tables or ext4 extents). It compiles a sequential list of physical storage extents—pairs of starting Logical Block Addresses (LBAs) and contiguous sector lengths on the physical USB flash drive that constitute the ISO image.

2. Building the Sector Mapping Table

Virtual optical media typically use a logical sector size of 2048 bytes, whereas underlying physical flash drives standardly expose 512-byte or 4096-byte sectors.

Ventoy allocates a small memory buffer to store a sector translation table. This table maps:

  • Virtual Optical LBA: The contiguous logical addresses expected by an ISO9660 or UDF file system (starting at virtual sector 0).
  • Physical Device LBA: The actual hardware addresses where the corresponding data resides on the physical storage device, adjusting for sector size differences (e.g., one 2048-byte ISO sector corresponds to four contiguous 512-byte physical sectors).

If the ISO file is fragmented across multiple non-contiguous physical blocks, the mapping table contains multiple segment entries to translate contiguous virtual offsets into their fragmented physical counterparts.

3. Firmware Interface Hooking

To make the ISO appear as a bootable optical drive before an operating system kernel loads, Ventoy hooks the active firmware interface:

  • Legacy BIOS: Ventoy hooks INT 13h, the standard BIOS disk service interrupt. It registers a virtual drive index (such as 0x9F or by remapping the CD-ROM drive ID) and intercepts read calls (AH=02h or extended read AH=42h). When a read request arrives for the virtual drive, Ventoy translates the requested virtual sector using its memory table and issues a revised read request to the physical USB drive ID.
  • UEFI: Ventoy creates a synthetic handle in the UEFI system table and installs instances of EFI_BLOCK_IO_PROTOCOL and EFI_DEVICE_PATH_PROTOCOL. Operating system bootloaders (like GRUB or Windows Boot Manager) read from this protocol, unaware that its ReadBlocks method executes Ventoy's translation logic rather than reading directly from optical hardware.

4. Transitioning to the Kernel Space

Firmware-level hooks become inactive once a loaded operating system kernel transitions to protected or long mode and initializes its own native storage drivers. To maintain access to the mapped ISO sectors without physical extraction, Ventoy injects runtime transition components:

  • Linux: Ventoy patches or hooks into the initial RAM disk (initramfs). During early user-space boot, a Ventoy runtime script detects the physical USB device, uses the Device Mapper (dm-linear) or loopback infrastructure to recreate the contiguous block device from the mapped sectors, and mounts it to the location the installer expects (such as /cdrom).
  • Windows: Ventoy injects an in-memory disk driver (ventoy.sys) or leverages Windows Setup hooks to present a virtual SCSI/CD-ROM device backed by the physical USB partition and the sector mapping layout.

Through this multi-stage mapping pipeline, read requests targeted at the virtual optical drive are translated on the fly into raw reads against the host USB storage.
