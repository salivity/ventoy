How Ventoy Handles Kaspersky Rescue Disk Partitions

Kaspersky Rescue Disk requires a writable storage location during boot to unpack system components, save scan logs, and store updated antivirus signatures. In standard live USB environments, this poses a problem for read-only ISO bootloaders. This article explains the technical mechanisms Ventoy uses to handle Kaspersky Rescue Disk's writable partition demand, detailing its automated boot hooks, persistence plugins, and partition handling.

The Kaspersky Rescue Disk Requirement

Kaspersky Rescue Disk (KRD) is built on a customized Gentoo Linux live environment. During its initialization, the startup scripts search for a local, writable partition—traditionally labeled KRD20_DATA—to initialize runtime directories such as /var and /tmp. If KRD cannot locate or mount a writable FAT32, exFAT, or NTFS partition, the boot process halts or fails to initialize the graphical interface and definition updates.

When booting an unextracted ISO directly, standard bootloaders present the image as a read-only optical medium (iso9660), which fails KRD's native write checks.

Ventoy's Dynamic Boot Interception

Ventoy resolves this issue without modifying the underlying ISO file on disk. When you select the Kaspersky Rescue Disk ISO from the Ventoy boot menu, Ventoy performs on-the-fly runtime patching:

  1. Initrd Hooking: Ventoy intercepts the boot loader configuration (GRUB2) and injects custom hooks into KRD’s initial RAM disk (initramfs).
  2. Mount Script Patching: Ventoy modifies the live boot scripts responsible for locating the storage medium. Instead of demanding an isolated physical partition formatted specifically for Kaspersky, Ventoy redirects the read-write overlays.
  3. RAM Disk Overlay Creation: If no designated persistent storage is detected, Ventoy instructs the environment to allocate an overlay file system entirely in memory (RAM). This satisfies KRD's writable filesystem check, allowing the scan engine, graphical interface, and core tools to load smoothly.

Enabling Real Write Support via Persistence

While Ventoy's automatic patching allows KRD to boot into memory, any downloaded virus databases or scan logs are discarded once the computer reboots. To maintain permanent writable storage, Ventoy leverages its persistence plugin system.

Ventoy allows users to attach a raw, formatted image file (such as an ext4 or FAT32 image) to the KRD ISO using the ventoy.json configuration file:

{
    "persistence": [
        {
            "image": "/krd.iso",
            "backend": "/krd_data.dat"
        }
    ]
}

During boot, Ventoy maps this image file as a virtual block device and presents it to KRD. KRD mounts this virtual container as its writeable backing store, enabling persistent virus definition updates and configuration retention between reboots without altering the partition structure of the Ventoy USB drive.

The Dedicated Partition Alternative

For environments where virtual persistence images are not used, Ventoy allows users to reserve space at the end of the USB drive during installation. Users can format this extra space as a standard FAT32 partition and label it KRD20_DATA.

Because Ventoy presents the underlying physical disk structure directly to the booted Linux kernel, KRD's native discovery scripts detect this labeled partition automatically, mounting it as the primary data directory without requiring software overlays.
