Why Ventoy Doesn't Require Contiguous Disk Clusters

Ventoy has fundamentally modernized USB multi-booting by eliminating the need to store ISO files in contiguous disk sectors. Traditional multi-boot loaders, such as older GRUB4DOS implementations, relied on direct physical sector mapping, which caused boots to fail whenever files became fragmented across non-adjacent clusters. Ventoy avoids this limitation by utilizing filesystem-level drivers, in-memory sector mapping, and runtime I/O hooking that reconstructs fragmented files dynamically in both UEFI and legacy BIOS environments.

The Limitation of Legacy Multi-Boot Tools

Legacy multi-boot software often relies on low-level BIOS disk interrupts (primarily INT 13h) to map an ISO file into a virtual CD-ROM drive. In traditional architectures:

  • Simple Sector Redirection: The bootloader passes a simple linear equation to the BIOS: a single starting Logical Block Address (LBA) and the total block length.
  • Lack of Filesystem Awareness: The legacy BIOS interrupt handler cannot parse modern filesystems like exFAT, NTFS, or Ext4. It cannot navigate File Allocation Tables (FAT) or Master File Tables (MFT) to find individual scattered fragments.
  • Failure on Fragmentation: If an ISO file is split across non-contiguous clusters due to normal disk wear or rewriting, the simple start + length mapping points to unrelated data halfway through the boot process, causing the bootloader to halt with an error stating the file is not contiguous.

To solve this, older solutions forced users to run defragmentation utilities (such as WinContig) to rearrange files into a single, uninterrupted physical chain before booting.

How Ventoy Eliminates the Contiguity Requirement

Ventoy bypasses the contiguous file requirement by shifting the responsibility of file resolution from physical disk structures to runtime software abstraction layers.

1. Embedded Filesystem Drivers in GRUB2

Ventoy uses a heavily customized GRUB2 core that includes native read drivers for nearly all common filesystems, including exFAT, NTFS, FAT32, ext2/ext3/ext4, UDF, and XFS. When you select an ISO, Ventoy does not merely point to a raw disk sector; it parses the underlying filesystem directly to locate all fragments associated with that specific file.

2. Fragment List Construction (Extents Mapping)

Instead of requiring a single start and end point, Ventoy builds an internal "extent map." This is an in-memory lookup table containing an array of sector ranges:

  • Fragment 1: LBA 1000 to 2000
  • Fragment 2: LBA 4500 to 8000
  • Fragment 3: LBA 12000 to 15000

Because this map resides in RAM, fragmentation has no impact on Ventoy’s ability to locate the complete dataset of the image file.

3. Dynamic Firmware I/O Hooking

To make this extent map readable to the booting operating system, Ventoy hooks directly into low-level firmware execution:

  • In UEFI Mode: Ventoy hooks the UEFI BlockIO and DiskIO protocols. When the booting OS kernel asks firmware services to read sector X of the virtual disc, Ventoy intercepts the request, checks its extent map, translates sector X into the corresponding physical cluster, and fetches the data seamlessly.
  • In Legacy BIOS Mode: Ventoy hooks the BIOS INT 13h interrupt handler with dynamic redirection logic that references the extent table instead of relying on a fixed linear block.

4. OS-Level Device Remapping

When a kernel initializes, it takes over disk control from UEFI or BIOS, normally breaking firmware-level hooks. Ventoy overcomes this by packaging runtime hooks (such as custom initramfs scripts for Linux or loopback filter drivers for Windows). These runtime components read the virtual disk directly from the filesystem where the ISO resides, allowing the operating system to maintain access to the fragmented ISO image until the boot process is complete.
