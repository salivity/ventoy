How Ventoy ACPI Table Injection Plugin Works

Ventoy's ACPI (Advanced Configuration and Power Interface) table injection plugin allows users to dynamically insert or replace hardware description tables in system memory during the pre-boot phase without flashing the motherboard's firmware. This article explains how Ventoy implements this feature, the underlying memory-hooking mechanisms it uses to override firmware data, and how the configuration process bridges custom ACPI binaries with bootable ISO files.

The Purpose of ACPI Table Injection

Motherboard firmware provides ACPI tables (such as DSDT, SSDT, and SLIC) to the operating system to describe hardware topology, manage power states, and expose manufacturer configuration data. In scenarios where a user needs to fix hardware detection bugs, patch broken DSDT routines, or supply specialized tables (such as software licensing tables) without flashing the physical BIOS/UEFI ROM, memory injection is the primary solution. Ventoy streamlines this by automating the insertion process during the bootloader execution phase.

How the Plugin Operates Under the Hood

Ventoy functions through a custom GRUB2-based environment. When an operating system image is selected for booting, the ACPI plugin alters the system's memory-resident firmware tables before passing execution control to the target OS kernel or secondary bootloader:

  1. Memory Discovery and Hooking: In a standard boot sequence, the firmware creates an ACPI pointer structure known as the Root System Description Pointer (RSDP) in system memory. The RSDP points to the Root System Description Table (RSDT) in 32-bit environments or the Extended System Description Table (XSDT) in 64-bit environments. Ventoy locates this structure in the host's physical memory.
  2. Table Insertion or Replacement: Ventoy allocates reserved memory for the user-provided ACPI binary file. If the binary represents a supplemental table (such as an SSDT), Ventoy adds a new entry pointer to the RSDT/XSDT array. If the binary is intended to replace an existing core table (such as a DSDT), Ventoy modifies the pointer in the Fixed ACPI Description Table (FADT) to refer to the newly loaded memory address instead of the original firmware address.
  3. Checksum Recalculation: Every ACPI table must have a valid checksum where the sum of all bytes equals zero modulo 256. When Ventoy modifies the RSDT, XSDT, or FADT, it recalculates and rewrites the checksum byte. This ensures the operating system's ACPI parser accepts the updated tables without throwing an initialization error.
  4. Boot Handoff: Once the tables are patched in RAM, Ventoy transfers control to the ISO's native bootloader. The operating system kernel initializes its ACPI subsystem, reads the patched memory structures, and executes using the modified hardware instructions. Because these changes reside strictly in volatile RAM, the physical motherboard firmware remains entirely untouched after a reboot.

Configuration and Matching Logic

The plugin relies on Ventoy's standard configuration file, ventoy.json, located inside the ventoy directory on the first partition of the USB drive. Users supply compiled ACPI machine language (.aml) or raw binary (.bin) dumps alongside the configuration file.

The plugin matches tables to specific images using either explicit file paths, directory matching, or global definitions:

{
    "acpi": [
        {
            "image": "/ISO/Windows11.iso",
            "acpi": "/ventoy/acpi/custom_table.aml"
        },
        {
            "image": "/Linux",
            "acpi": [
                "/ventoy/acpi/ssdt1.aml",
                "/ventoy/acpi/ssdt2.aml"
            ]
        }
    ]
}

Ventoy supports assigning a single table or an array of multiple tables to an image. If a directory path is specified instead of a single image, all bootable ISOs within that directory inherit the injected tables.

Compatibility and Limitations

The ACPI injection plugin works across both Legacy BIOS and UEFI modes. However, it requires correctly compiled binary files; invalid tables or incompatible opcode instructions within an injected AML file will cause the target operating system's kernel to panic or fail during boot. Furthermore, operating systems that bypass standard firmware memory tables and construct their own ACPI state directly from low-level hardware probes may ignore the injected pointers.
