How Ventoy Isolates Bootloader From Storage Space

Ventoy secures its boot functionality by physically and logically segregating the core bootloader environment from user-accessible storage through a dedicated dual-partition architecture. By dividing a flash drive into a protected, hidden system partition for boot routines and an expansive, user-facing data partition for ISO files, Ventoy prevents accidental file overwrites, bootloader corruption, and file-system conflicts. This article explains the technical mechanics behind this separation, detailing how partition tables, UEFI-compliant file systems, and in-memory disk emulation work together to keep the core boot system isolated.

The Dual-Partition Architecture

When Ventoy formats a USB drive, it creates two distinct partitions using standard MBR or GPT partitioning schemes:

  • Partition 1 (Ventoy Data Partition): This partition consumes the vast majority of the drive's capacity. It is formatted by default with the exFAT filesystem, though users can reformat it to NTFS, ext4, Btrfs, or XFS. This space is solely reserved for storing ISO, WIM, IMG, and VHD files, alongside normal user data.
  • Partition 2 (VTOYEFI System Partition): This is a small, reserved partition (typically 32 MB) located at the physical end of the drive. It is formatted exclusively with FAT16 or FAT32 to ensure universal compatibility with UEFI firmware specifications and legacy BIOS standards.

Isolation via the VTOYEFI Partition

Ventoy achieves operational isolation by restricting all boot executable files—including GRUB core binaries, drivers, and EFI loaders—to Partition 2.

Because modern operating systems like Windows natively hide or disregard secondary partitions on removable media that are marked with specific partition types (such as EFI System Partition GUIDs), users typically cannot view or alter Partition 2 during standard desktop use. This prevents accidental deletion, formatting, or malware-induced tampering of the essential boot executable binaries.

In-Memory Disk Emulation

Ventoy avoids integrating the bootloader with the storage partition by using runtime memory hooks rather than modifying stored files:

  1. Read-Only ISO Execution: When a user selects an ISO located on Partition 1, the bootloader in Partition 2 does not extract or modify the image on the disk.
  2. Runtime Interception: Ventoy hooks into the system's firmware interrupts (BIOS Int 13h or UEFI Block I/O protocols). It constructs a virtual optical drive entirely in system RAM that points to the contiguous physical sectors of the ISO file stored on Partition 1.
  3. OS Hand-off: When the target operating system boots, it reads from this virtual optical device. The data partition remains untouched in terms of system structure, ensuring the host OS installer cannot alter the Ventoy boot code.

Preservation During Updates

This strict separation also isolates maintenance procedures. When updating Ventoy to a newer release, the Ventoy installer only overwrites the data inside Partition 2. The partition table offsets and Partition 1 remain completely intact, allowing users to update bootloader code without reformatting the drive or re-copying large disk images.
