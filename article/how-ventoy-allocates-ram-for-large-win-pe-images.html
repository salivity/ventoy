How Ventoy Allocates RAM for Large WinPE Images

This article explains how Ventoy handles RAM drive allocation and memory management when booting large Windows Preinstallation Environment (WinPE) images. It explores the differences between standard virtual mapping and complete memory loading, detailing how Ventoy interacts with UEFI and BIOS memory tables, Microsoft’s native ramdisk drivers, and underlying storage hardware to boot large images efficiently without exhausting system resources.

Default Mode: Virtual Mapping via Driver Injection

By default, Ventoy does not copy the entire WinPE ISO into system RAM. Loading a multi-gigabyte ISO directly into memory would cause out-of-memory crashes on systems with limited physical RAM. Instead, Ventoy uses a virtual mapping architecture:

  1. Pre-OS Hooking: During the initial boot phase, Ventoy hooks the BIOS interrupt vector (INT 13h) in legacy mode or hooks UEFI runtime services to emulate a virtual CD/DVD drive pointing directly to the ISO stored on the physical USB drive.
  2. Boot Manager Execution: The system loads the standard Windows Boot Manager (bootmgr or bootmgr.efi) from the virtual disk.
  3. RAM Disk Allocation for the WIM: The Windows Boot Manager uses Microsoft’s native ramdisk.sys driver and the boot.sdi specification to allocate a RAM disk exclusively for the compressed boot.wim file, not the entire ISO.
  4. Runtime Driver Injection: To prevent Windows from losing access to the ISO once the kernel initializes and BIOS/UEFI hooks are discarded, Ventoy injects a runtime driver (ventoy.sys) on the fly. This driver identifies the host USB drive and transparently remounts the full ISO as a logical drive inside WinPE, allowing external tools and secondary files to run without consuming system RAM.

Memdisk Mode: Complete Physical RAM Allocation

When you explicitly configure Ventoy to boot an image using Memdisk mode (via secondary boot menus or hotkeys), Ventoy changes its allocation strategy and loads the entire image into physical RAM before execution:

  • Contiguous Memory Reservation: Under UEFI, Ventoy queries the memory map via GetMemoryMap() and invokes AllocatePages() with the AllocateAnyPages or AllocateAddress type to reserve a contiguous block of physical memory matching the exact size of the ISO. In legacy BIOS mode, it modifies the system E820 memory map via INT 15h to mark the designated region as reserved.
  • Payload Transfer: Ventoy reads the ISO sequentially from the USB storage controller and copies the raw data directly into the allocated memory buffer.
  • Emulation Handover: The allocated RAM range is mapped as a virtual drive. Because the entire ISO resides in memory, access speeds match the system’s memory bandwidth, and the physical USB drive can be safely removed after the payload is transferred.

Memory Overhead and Scratch Space Considerations

When booting large WinPE images, memory exhaustion typically occurs due to the interaction between the image payload and Windows PE's internal requirements:

  • The WIM-to-RAM Ratio: A boot.wim file inside a WinPE ISO is compressed. When loaded into memory by ramdisk.sys, the system reserves physical RAM matching the uncompressed size of the image along with the metadata footprint.
  • WinPE Scratch Space: WinPE allocates a temporary writeable RAM buffer, known as scratch space (ranging from 32 MB to 512 MB, configured within the WIM). This memory is layered on top of the allocated RAM disk.
  • Total RAM Footprint: In default mode, the total physical RAM required equals the size of the extracted boot.wim, plus the designated scratch space, plus the minimal Windows runtime overhead. In Memdisk mode, the total RAM required equals the size of the entire ISO, plus the decompressed boot.wim, plus the scratch space, making default mode significantly more reliable for large, customized rescue environments.
