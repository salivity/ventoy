How Ventoy Injection Plugin Injects Drivers

The Ventoy Injection Plugin provides a seamless method to inject custom hardware drivers, scripts, and configuration files into an operating system installer during boot without modifying the original ISO file. By pairing an untouched ISO with a compressed archive through a simple JSON configuration, Ventoy dynamically loads the necessary files directly into the installer's memory environment at runtime. This approach allows administrators to deploy drivers for unsupported storage controllers, network cards, and chipsets without needing to repack, slipstream, or invalidate the checksums of official OS distribution media.

The Mechanics of In-Memory Injection

Ventoy operates at the bootloader level using a customized GRUB/iPXE core. When an operating system boots, the installer relies on a temporary boot environment—such as the Windows Preinstallation Environment (WinPE) for Windows or an initial ramdisk (initrd/initramfs) for Linux.

Instead of writing data to physical disks, the injection plugin hooks into this early boot sequence. When you select an ISO, Ventoy reads the designated driver archive (typically a .7z, .zip, or .cpio file) from the USB drive and overlays its contents directly into the system's memory before handing control over to the operating system kernel.

The Role of ventoy.json

The entire process is controlled via the ventoy.json configuration file located in the ventoy directory on the USB drive. Within this file, the injection array maps specific ISO images to specific driver archives.

A standard configuration designates:

  • The target ISO path: The image you intend to boot.
  • The archive path: The location of the compressed file containing the drivers.

When the user launches an ISO that matches an entry in ventoy.json, Ventoy automatically activates the injection routine.

Injecting Drivers into Windows (WinPE)

For Windows installations, missing storage controllers or RAID drivers often lead to the installer failing to detect hard drives. The injection plugin solves this through a multi-step execution:

  1. Extraction to the Virtual Ramdisk: During WinPE startup, Ventoy mounts the injection archive and extracts its contents directly to the root of the WinPE memory disk (the X: drive).
  2. Automated Discovery via Scripts: The extracted files typically include an automated script (such as winpeshl.ini, a batch script, or integration with unattend.xml).
  3. Execution of pnputil or drvload: Before setup.exe launches, the script uses native Windows utilities—like drvload.exe or pnputil.exe—to load the .inf driver files stored in the memory disk.
  4. Installer Handoff: Once the driver is resident in memory, the Windows installer gains access to previously unrecognized hardware, allowing the installation to proceed normally.

Injecting Drivers into Linux Installers

Linux installers rely on an initrd image loaded into memory to supply baseline drivers before mounting the root filesystem. Ventoy interacts with Linux kernels by appending the injection archive as an additional ramdisk layer.

  1. Secondary Initrd Appending: Ventoy passes the injection archive (typically formatted as a .cpio archive) to the Linux bootloader alongside the original initrd.
  2. Kernel Overlay: The Linux kernel unpacks all provided initrd archives sequentially into the root memory filesystem (rootfs). The custom drivers or kernel modules (.ko files) become instantly available.
  3. Module Loading: Driver Update Disks (DUD), OEM directories, or distribution-specific installer scripts (such as Kickstart or Preseed hooks) detect the unpacked kernel modules and load them using modprobe or udev.

Key Benefits Over Traditional Slipstreaming

  • Integrity Retention: The original ISO files remain clean, bit-for-bit identical to the vendor release, preserving digital signatures and SHA hashes.
  • Rapid Maintenance: Updating a driver requires only updating the files inside the compressed archive, rather than rebuilding a multi-gigabyte ISO.
  • Granular Control: Different archives can be assigned to different hardware profiles or ISO versions within the same configuration file.
