How Ventoy Boots ISO Files Without Extraction

Ventoy allows users to boot multiple operating systems from a single USB drive simply by copying raw ISO files onto the storage partition. Instead of unpacking ISO contents or reformatting the drive for every new image, Ventoy dynamically hooks into the system's firmware and kernel boot stages. It maps the ISO’s storage sectors directly into system memory, creating a virtual optical drive that the operating system recognizes as real installation media.

The Dual-Partition Architecture

When prepared with Ventoy, a USB drive is divided into two distinct partitions:

  1. The System Partition: A tiny, hidden partition (usually formatted as FAT) that contains the bootloader binaries for both legacy BIOS and modern UEFI architectures.
  2. The Data Partition: A large partition (formatted as exFAT, NTFS, or ext4) where users simply drag and drop unaltered .iso, .img, or .vhd files.

When the computer starts, the hardware executes the bootloader from the small system partition, running a customized build of GRUB2. This interface scans the data partition, reads its file system, and generates a boot menu listing every detected ISO.

Firmware-Level Hooking (BIOS and UEFI)

Under traditional booting methods, tools like Rufus extract the ISO's file structure directly onto the USB file system or write the image raw (using dd), destroying any existing drive contents. Ventoy bypasses this using firmware-level emulation.

  • Legacy BIOS: Ventoy hooks the INT 13h interrupt vector in memory. INT 13h is the legacy BIOS service used for reading and writing to disk drives. Ventoy intercepts these read requests and redirects them to the exact physical sectors where the ISO resides on the USB drive.
  • Modern UEFI: Ventoy intercepts UEFI runtime services, specifically hooking into the EFI_BLOCK_IO_PROTOCOL. It creates a virtual handle for a CD-ROM device, feeding the firmware data directly from the ISO file stored on the data partition.

At this initial stage, the firmware believes a physical CD/DVD drive is attached to the system and boots the bootloader embedded inside the ISO (such as ISOLINUX or GRUB).

Transitioning to the OS Kernel

Emulating an optical drive at the firmware level is only half the battle. As soon as an operating system kernel (such as the Linux kernel or the Windows NT kernel) initializes, it discards BIOS interrupts and UEFI protocols, loading its own native hardware drivers. Ordinarily, this causes the boot process to fail because the OS loses sight of the virtual optical drive and searches for physical installation media.

Ventoy solves this through runtime kernel interception:

  • Linux Bootstrapping: Ventoy hooks into the OS’s initial RAM disk (initramfs or initrd). When the Linux kernel boots, a lightweight Ventoy runtime hook executes before the root file system is mounted. This script locates the original ISO file on the USB drive, creates a loopback block device (using device-mapper), and mounts it to the location where the distribution's installer expects to find physical installation media.
  • Windows Bootstrapping: For Windows installations, Ventoy injects a custom runtime driver into the Windows Preinstallation Environment (WinPE) during memory initialization. This driver mounts the target ISO file as a virtual SCSI/SATA optical drive before the Windows setup process checks for installation files.

Sector Mapping Over Memory Caching

A common misconception is that Ventoy copies the entire ISO file into system RAM to boot it. While Ventoy includes an optional "memdisk" mode for small diagnostic images, its standard operation uses sector mapping rather than RAM loading.

Ventoy determines the physical sector addresses (LBAs) of the ISO file on the USB drive. It then presents these sectors to the operating system on demand. Because the file is read in real time directly from the storage flash, Ventoy can boot massive multi-gigabyte ISO files instantly on systems with minimal RAM.
