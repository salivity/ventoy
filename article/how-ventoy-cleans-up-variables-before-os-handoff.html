How Ventoy Cleans Up Variables Before OS Handoff

Ventoy relies on a heavily modified GRUB2 core and custom UEFI/BIOS shims to manage boot options, set runtime parameters, and map ISO files to virtual storage before booting an operating system. To ensure seamless operation, Ventoy cleans up its temporary state and isolates runtime variables using standard UEFI memory-typing conventions, volatile variable attributes, and execution hooks triggered at ExitBootServices. This approach allows Ventoy to maintain virtual disk access for the target kernel while safely discarding its internal bootloader variables and scratchpad memory.

During the pre-boot phase, Ventoy executes scripts and stores parameters—such as ISO paths, hardware detection flags, and user configurations—within GRUB’s internal memory pool and the UEFI variable store. For memory-allocated data, Ventoy assigns these buffers to EfiBootServicesData or EfiBootServicesCode. Under the UEFI specification, all memory classified under boot services is designated as transient; it is strictly reserved for pre-boot operations and is marked to be reclaimed by the operating system kernel once the boot process transitions out of firmware services.

To clean up variables exposed through firmware interfaces, Ventoy assigns volatile flags to its custom UEFI environment variables. These variables are created without the EFI_VARIABLE_NON_VOLATILE attribute, meaning they exist exclusively in system RAM during the active boot phase. Consequently, they do not write to the physical NVRAM chip, preventing persistent clutter or interference with the target operating system's variable namespace. Any runtime variables used exclusively for ISO chaining are either explicitly deleted prior to kernel execution or naturally drop out of scope when firmware tables are finalized.

The physical handoff occurs when the operating system loader calls the UEFI interface function ExitBootServices(). Ventoy hooks this function to complete its state transition. Upon interception, Ventoy uninstalls its temporary protocol interfaces and deregisters pre-boot event listeners, ensuring that CPU register states and memory management structures return to a standard state expected by the OS kernel.

The only component that persists past this cleanup is the minimal runtime disk abstraction layer, typically preserved in memory marked as EfiRuntimeServicesData or EfiReservedMemoryType. This persistent segment contains only the essential logic required to intercept disk read requests and route them to the underlying ISO file, stripped of all setup variables, menu scripts, and interface configurations.

In legacy BIOS mode, a comparable procedure takes place. Ventoy establishes its runtime variables in conventional memory used by the bootloader stage. Once the target kernel is loaded, Ventoy relocates a minimal INT 13h interrupt service routine to the Extended BIOS Data Area (EBDA) or top of conventional memory, restores the default CPU register states, and relinquishes the remaining memory space. The incoming kernel then safely overwrites the original memory footprint containing Ventoy's temporary execution variables.
