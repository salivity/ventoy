Why Ventoy Uses Specific Partition GUIDs and Labels

Ventoy is an open-source utility that creates bootable USB drives capable of launching multiple operating systems directly from raw ISO and image files. To achieve this seamless, multi-boot capability across vastly different computer architectures, Ventoy relies strictly on specific partition Globally Unique Identifiers (GUIDs) and filesystem labels. This overview explains how these identifiers enable the Ventoy bootloader to reliably locate its core system files, distinguish between user data and internal runtime environments, and maintain cross-platform stability without depending on unpredictable hardware enumeration.

The Problem of Inconsistent Disk Numbering

In low-level pre-boot environments (both legacy BIOS and modern UEFI), device enumeration is volatile. A USB drive assigned as hd0 or Disk 0 on one computer may be designated as hd1, hd2, or entirely different device handles on another, depending on the motherboard firmware, plugged-in peripherals, and controller configurations.

Hardcoding device paths into boot configurations is impossible for a portable utility. Ventoy avoids this limitation by scanning all connected storage devices at boot time for explicit filesystem labels and GUID markers, ensuring it always finds its payload regardless of which port or controller hosts the drive.

Managing Ventoy's Dual-Partition Architecture

When a disk is formatted with Ventoy, it is intentionally divided into two separate partitions:

  1. Partition 1 (Data Volume): Formatted by default with exFAT (though NTFS, ext4, and other filesystems are supported). This is where users place ISO, WIM, and IMG files.
  2. Partition 2 (Boot/System Volume): A small, protected FAT-formatted partition that holds the core boot files, including the GRUB core image, EFI binaries, drivers, fonts, and runtime scripts.

To transition from the initial firmware handover to the interactive boot menu, the pre-boot loader must immediately locate Partition 2. Ventoy searches specifically for the volume label VTOYEFI. Using this predetermined label allows runtime scripts to locate, verify, and mount the bootloader slice without needing to inspect the contents of every storage drive attached to the machine.

Partition Type GUIDs in GPT Schemes

On GPT-partitioned disks, each partition possesses both a unique Partition GUID and a Partition Type GUID. Ventoy leverages standardized and custom Type GUIDs to fulfill specific low-level tasks:

  • OS Protection: By setting specific partition type attributes and GUIDs, Ventoy instructs desktop operating systems (like Windows) to treat the secondary boot partition as a hidden or system-reserved volume. This prevents users from accidentally deleting, reformatting, or modifying the core boot infrastructure.
  • Firmware Compliance: UEFI firmware specifications require specific EFI System Partition (ESP) type GUIDs (C12A7328-F81F-11D2-BA4B-00A0C93EC93B) to recognize the partition as bootable. Ventoy ensures the secondary partition matches these specifications so motherboards automatically index the .efi loaders.

Decoupling Boot Files from User Storage

Because users are permitted to reformat, encrypt, or change the filesystem of Partition 1 to suit their needs, Ventoy cannot rely on predictable paths or structures on the main data partition.

By anchoring its core dependencies to an isolated, distinctly labeled filesystem (VTOYEFI) with strict GUID attributes, the primary boot mechanism remains entirely decoupled from user data. The bootloader reliably initializes its required drivers and hooks into the hardware first, before attempting to parse whatever arbitrary filesystem the user has chosen for their bootable images.
