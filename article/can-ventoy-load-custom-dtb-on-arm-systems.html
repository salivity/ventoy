Can Ventoy Load Custom DTB on ARM Systems?

Ventoy does not natively support loading or swapping custom Device Tree Blobs (DTBs) through its boot menu or configuration files on ARM systems. While Ventoy provides official support for the ARM64 (aarch64) architecture, it depends on standard UEFI environments to initialize hardware rather than handling board-specific device tree injection. This article breaks down how Ventoy handles ARM booting, why custom DTB loading is absent, and the practical workarounds available for ARM single-board computers.

Why Ventoy Lacks Native DTB Management

Ventoy is designed around the standard PC boot model, which it extends to ARM via the UEFI standard. On typical x86 systems, hardware configuration is exposed automatically through ACPI tables. On ARM platforms, non-standardized hardware requires a Device Tree Blob (.dtb) to inform the Linux kernel about the board's peripheral addresses, GPIO pins, clocks, and memory layout.

Ventoy relies on GRUB2 and UEFI to launch boot images. Because Ventoy assumes an established UEFI layer is already running on the target device, it delegates hardware discovery to that underlying firmware. Ventoy's core image parser does not provide a native menu option, global plugin, or user interface to specify an external DTB file to pass to an ISO's kernel.

The Role of UEFI Firmware on ARM

To run Ventoy on an ARM system—such as a Raspberry Pi or a Rockchip-based device—the board must first boot a UEFI implementation (such as EDK2 or Tianocore) from its initial storage.

When UEFI initializes on an ARM board, it generally accomplishes one of two things:

  1. It provides ACPI tables to the operating system.
  2. It loads the board's designated DTB into memory and exposes it via the UEFI configuration table.

Because the underlying UEFI firmware typically registers the device tree before Ventoy even executes, Ventoy simply passes whatever hardware description table the firmware has already loaded directly to the target operating system.

Workarounds for Booting Custom DTBs

If an operating system or hypervisor requires a specific or modified DTB that is not supplied by the firmware or the ISO itself, you cannot rely on Ventoy's automated loader. Instead, you must use one of the following methods:

  • Configure the Underlying UEFI Layer: Ensure the EDK2/UEFI image flashed to your board's SPI flash or primary storage contains the updated DTB. Most ARM UEFI implementations allow you to point the firmware directly to an updated DTB stored in the firmware partition.
  • Use Ventoy's Custom GRUB Extension: Ventoy supports extending its menu via a user-created ventoy_grub.cfg file located in the ventoy directory of the USB drive. Within this script, you can write custom GRUB menu entries utilizing GRUB’s native devicetree command (for example: devicetree /path/to/custom.dtb) to manually load a kernel, initramfs, and DTB. This bypasses Ventoy's automated ISO loop-mounting mechanism.
  • Modify the Target OS Image: For Linux distributions distributed as raw disk images (.img), mount the image prior to placing it on the Ventoy drive and replace the default .dtb file inside the image's boot partition with your custom version.
