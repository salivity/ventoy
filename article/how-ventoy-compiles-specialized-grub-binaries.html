How Ventoy Compiles Specialized GRUB Binaries

Ventoy relies on heavily customized GNU GRUB 2 implementations to achieve its multi-architecture, multiboot capabilities without unpacking ISO contents. Compiling these specialized binaries requires an automated toolchain pipeline that leverages isolated container environments, custom source patches, cross-platform configuration switches, and dynamic image packaging. This article details each stage of that compilation process, explaining how vanilla GRUB source code is transformed into the specialized bootloaders used on Ventoy storage drives.

Containerized Build Environment

To ensure reproducibility across diverse host systems, the Ventoy build system coordinates compilation inside a standardized Docker container (predominantly based on legacy CentOS or Debian environments). This container houses the exact toolchains required for target platforms: standard GNU Compiler Collection (GCC) suites, cross-compilers targeting x86, x86_64, ARM64, and MIPS64EL, and requisite build dependencies such as Automake, Autoconf, Bison, and Flex. Executing the build scripts inside the container prevents host system library drift from corrupting low-level boot code.

Applying Ventoy Custom Patches

The compilation routine initiates via automated shell scripts (such as buildgrub.sh in the source repository). Before invoking the GNU build system, the scripts apply a comprehensive set of custom C code modifications and patches over vanilla GRUB 2 source trees. These modifications include:

  • Virtual Disk Drivers: Custom block-device implementations (such as Ventoy's virtual disk device, vtoy) that permit loop-mounting disk images directly from host filesystems into memory or mapped blocks.
  • Enhanced Filesystem Support: Custom and extended filesystem drivers capable of traversing exFAT, NTFS, ext4, UDF, and ISO9660 partitions reliably in pre-boot environments.
  • Hook Handlers: Runtime interception routines that monitor memory regions and patch OS boot parameters on the fly, enabling Windows and Linux kernel loaders to recognize Ventoy's mapped virtual media.

Multi-Architecture Autotools Configuration

Once the source tree is patched, the build scripts loop through every supported target platform. For each architecture, the script runs the GNU Autotools ./configure script with specialized platform flags:

  • i386-pc for legacy BIOS
  • i386-efi for 32-bit UEFI
  • x86_64-efi for standard 64-bit UEFI
  • arm64-efi (AArch64) for 64-bit ARM UEFI
  • mips64el-efi for Loongson/MIPS-based systems

During this stage, compiler optimization flags (-Os or -O2) are applied alongside strict freestanding C options (-ffreestanding, -fno-builtin) to ensure the compiled modules omit standard C runtime library calls that do not exist during the pre-boot phase.

Compiling Modules and Utilities

Following configuration, standard make routines compile the core GRUB kernel (kernel.exec) and dynamic module objects (.mod files) for the designated platform. Because Ventoy operates across multiple storage buses, modules handling USB, AHCI, NVMe, partition tables (GPT and MBR), and crypto signatures are built systematically for each distinct target architecture.

Packing Monolithic Core Images

The final step uses GRUB's native utility, grub-mkimage, to assemble standalone executable binaries from the compiled modules. Instead of relying on an external filesystem to load modules sequentially, Ventoy bundles essential runtime drivers directly into monolithic executables (core.img for BIOS, bootx64.efi / bootia32.efi / bootaa64.efi for UEFI variants).

During this image creation step, the build scripts embed an early runtime configuration file directly into the image's memory space. This early configuration initializes the display, scans connected block devices for the Ventoy partition signature, loads secondary dynamic drivers, and passes control to the main Ventoy runtime menu. Completed binaries and accompanying runtime modules are compressed and placed into Ventoy’s installation directory structure for deployment to target USB media.
